# sonus: WH-1000XM6 Python 드라이버 & PyQt6 제어 앱 — 설계

## 목표

Sony WH-1000XM6를 Linux에서 완전 제어하는 순수 Python 드라이버(`sonus`)와,
그 위에 얹는 PyQt6 GUI를 만든다. 최종 목표는 Sony "Sound Connect" 앱이
제공하는 기능(ANC/앰비언트, 이퀄라이저, DSEE, 멀티포인트, 터치 제어 커스터마이징,
자동 전원 끄기, 배터리/펌웨어 조회 등)을 상호운용성 목적으로 재현하는 것.

## 범위

- **플랫폼**: Linux 전용 (BlueZ + classic Bluetooth RFCOMM). Windows/macOS는
  범위 밖이지만, 전송 계층을 추상화해 두어 나중에 이식 가능하게 설계한다.
- **기능**: Sony 앱과 동등한 전체 제어. 단, XM6 자체가 신제품이라 공개된
  프로토콜 표(SonyHeadphonesClient 등 커뮤니티 리버스엔지니어링 자료)는
  XM4/XM5 기준이다. 이 표는 **가설 시작점**으로만 쓰고, 실제 명령/응답은
  사용자 소유의 실기기(`58:18:62:1F:C9:CB`)에 직접 요청을 보내 관찰하고
  검증한다.
- **법적 원칙**: 관찰한 프로토콜 구조(데이터 묶음 형식, 명령 ID, 내용 데이터 배치)를
  상호운용성 목적으로 문서화하는 것은 허용 범위다(예: 한국 저작권법
  §101-4, EU 소프트웨어지침 §6, DMCA §1201(f)에 상응하는 리버스엔지니어링
  예외). 단, Sony의 코드·펌웨어·바이너리 자체를 복사·역어셈블 결과물째
  배포하지 않는다. `docs/protocol/README.md`에 이 원칙을 고지문으로 명시한다.

## 아키텍처: 계층 구조

각 계층은 바로 아래 계층만 안다. `sonus` 라이브러리 코드(`transport/`,
`protocol/`, `messages/`, `device/`)는 Qt를 import하지 않는다 — GUI는
교체 가능한 얇은 소비자여야 한다.

| 계층 | 경로 | 책임 | 아는 것 / 모르는 것 |
|---|---|---|---|
| L1 전송 | `src/sonus/transport/` | RFCOMM 소켓 연결, SDP로 채널 탐색, 끊김 감지·재연결(지수 백오프 3회) | 바이트만 안다. 소니 프로토콜 의미를 모른다 |
| L2 프로토콜 | `src/sonus/protocol/` | 프레임 인코딩/디코딩, 바이트 이스케이프, 체크섬, 시퀀스 번호, ACK 왕복, 명령별 타임아웃(기본 2초) | 프레임 구조는 알지만 명령의 의미는 모른다 |
| L3 메시지 | `src/sonus/messages/` | 명령별 페이로드 코덱. `registry.py`에 명령 ID → dataclass 매핑을 선언적으로 등록 | 각 명령의 바이트 배치를 안다. 기기 상태는 모른다 |
| L4 디바이스 | `src/sonus/device/` | 연결 수명주기, capability 협상(기기가 보고하는 지원 기능 목록 캐시), 상태 캐시, 타입 있는 async API, 이벤트 스트림 | 기기의 현재 상태를 안다. UI를 모른다 |
| CLI | `src/sonus/cli/` | 테스트·검증·덤프 도구. `sonus probe`(연결+정보덤프), `sonus sniff`(원시 바이트 타임스탬프 로깅), `sonus send <hex>`(임의 데이터 묶음 전송·응답 관찰) | L4 + 필요시 L2 직접 접근 |
| GUI | `src/sonus/gui/` | PyQt6 메인 창 + 시스템 트레이 | L4만 안다 |

### capability 기반 동적 UI

L4가 연결 시 기기의 지원 기능 목록을 조회해 캐시한다. GUI는 이 목록을 보고
탭/컨트롤을 동적으로 그린다. XM6 고유 기능이 발견되면 `messages/registry.py`에
항목만 추가하면 되고, GUI/CLI 코드는 손대지 않아도 된다.

### 데이터 묶음 형식 가설 (검증 대상)

공개 리버스엔지니어링 자료 기준 구조를 시작 가설로 둔다:
`0x3E`(시작) + 시퀀스 + 명령타입 + 길이 + 페이로드 + 체크섬 + `0x3C`(끝),
페이로드 내 `0x3E/0x3C/0x3D`는 `0x3D` + 보정바이트로 이스케이프.
XM6에서 이 구조가 실제로 맞는지는 `sonus sniff`/`sonus send`로 1일차에
실기기 대상으로 검증하고, 다르면 관찰한 대로 갱신한다.

```
sonus/

├── README.md
├── pyproject.toml
├── docs/
│   ├── protocol/           # 관찰 기록: 데이터 묶음 형식, 명령 표, 캡처 세션 로그 (고지문 포함)
│   └── superpowers/specs/  # 설계 문서
├── src/sonus/
│   ├── transport/
│   ├── protocol/
│   ├── messages/
│   ├── device/
│   ├── cli/
│   └── gui/
└── tests/
    ├── unit/              # 하드웨어 불필요, 항상 실행
    ├── hardware/          # 실기기 필요, pytest -m hardware 로만 실행
    └── fixtures/captures/ # 실측 바이트 캡처 → 회귀 테스트 자료
```

## GUI 설계

- **구성**: 메인 창(상태/ANC/EQ/기기설정 탭) + 시스템 트레이 아이콘. 트레이에서
  배터리 % 표시, ANC 모드 빠른 전환. 창을 닫아도 트레이에 상주하며 연결/해제를
  자동 감지한다.
- **스타일**: 심플. 화려한 애니메이션·장식 없음. 다크/라이트 모드 전환 가능,
  포인트 컬러는 파랑 계열 하나로 통일.
- **에러 노출**: raw exception을 절대 그대로 보여주지 않는다. 상태바에
  사람이 읽을 수 있는 문구로 변환해 표시(예: "기기 응답 없음, 재연결 중...").

## 테스트 전략

- `tests/unit/`: L2 프로토콜 인코딩/디코딩은 순수 함수라 하드웨어 없이
  전량 테스트 가능. `tests/fixtures/captures/`에 저장한 실측 바이트로
  회귀 테스트를 만든다.
- `tests/hardware/`: 실기기 필요. `pytest.mark.hardware`로 표시해 기본
  `pytest` 실행에서 제외하고, 검증 시에만 `pytest -m hardware`로 별도 실행.
- CI(로컬 한정, 헤드셋 없는 환경 포함)는 `tests/unit/`만으로 항상 초록불이
  유지되어야 한다.

## 구현 위임 방침

설계·계획·리뷰는 메인 세션에서 진행하고, 실제 코드 작성은 서브에이전트에
위임하되 모델은 Sonnet 또는 Haiku로 지정한다(Opus 사용 안 함). 기계적인
보일러플레이트·테스트 작성은 Haiku, 판단이 필요한 구현(프로토콜 코덱,
디바이스 상태 관리)은 Sonnet에 맡긴다.
